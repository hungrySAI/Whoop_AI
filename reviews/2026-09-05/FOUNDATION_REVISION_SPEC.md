# 根基修订规范 · 提议版

日期：2026-09-05。性质：交给 Codex 核实并实现的设计，不是已存在的系统。

## 1. 产品定位与边界

WHOOP 是第一数据源，不是系统的永久边界。产品仍然是用户自己的 WHOOP Personal Copilot：WHOOP 负责采集、官方计算和设备操作；外挂负责趋势、追问、训练、长期个人上下文和其他获准身体信息。

实现范围可以分批，但不要把“本批暂不实现”写成“架构永远不允许”。同时，未来可扩展不等于首期建设多租户 SaaS、微服务集群、实时流平台或通用医疗系统。

## 2. 四类约束

| 类别 | 示例 | 处理 |
|---|---|---|
| 长期真实性／安全底线 | 不伪造官方指标、不泄露凭据、不越权操作、不按穿戴值自动调药 | 由代码与测试强制，不能靠改提示词放开 |
| 外部能力／条款 | 个人 API 没有某资源、数据使用与保留条件 | 记录核查日期与实际权限；变化后可更新，不写成永久技术禁令 |
| 可配置默认 | 初始 90 日、60 分钟轮询、28 日基线、单一模型 | 参数化且有版本；原包已有大部分这些默认，不应误判为硬上限 |
| 迭代范围 | 首批不做 HealthKit、全日蓝牙、丰富前端、通知 | 保留必要接口，不建设空壳功能、不当作永久禁止 |

## 3. 目标结构

```text
数据适配器：WHOOP API / 官方导出 / 手工或CSV / 后续获准来源
                         ↓
接入服务：授权、使用策略、格式校验、去重、版本、任务
                         ↓
数据底座：受保护源版本 + 强类型领域数据 + 扩展指标
                         ↓
共享应用服务：查询 / 分析 / 上下文 / 计划日志 / 操作与权限
                  ↙             ↓              ↘
               Web            MCP/CLI         调度入口
                                ↓
                       模型适配与代理流程
                          ↙             ↘
                    稳定教练          探索分析
```

所有入口调用同一应用服务。MCP 是传输和工具适配层，不成为数据模型或业务逻辑中心。日常统计与模型服务解耦；业务服务与某个前端解耦。

默认仍是一个 Python 代码库、一个数据库、Web 进程和一个工作进程。模块数量按实际复杂度压缩，不需要为图中的每个框创建一个服务、仓库或独立框架。

## 4. 最小稳定契约

下面是逻辑对象，不要求每个对象单独一张表。可以从少量表和有类型的结构开始。

### 4.1 SourceConnection 与来源使用策略

`connection_id`、内部 `subject_id`、provider、外部账户绑定、能力状态、scope、同步状态、授权引用、来源使用／保留策略、核查时间。

同步凭据只在受保护秘密存储中；不要复制到普通领域记录。内部 ID 不使用 WHOOP user_id 作为全系统身份。当前只有一个人也可以有稳定 subject ID；不因此开发多租户系统。

### 4.2 SourceRecordRevision

连接、资源类型、外部 ID、内容哈希、来源版本／更新时间、应用获知时间、解析器版本、受保护 payload、删除状态、适用保留策略。

原始版本可被依法／按授权删除，不是永久不可变档案。只保留获准范围，缓存头等策略元信息采用明确白名单，不保存 Authorization 或整个 HTTP 请求。

### 4.3 Observation 与活动领域对象

观察值至少有指标定义、原值／单位、规范值／单位、测量时间或时间区间、时间精度、获取时间、来源、质量、版本与引用。

睡眠、运动、训练组次等保留具体结构和关系；不要把所有内容塞进单一键值表。WHOOP cycle 通过外部关联表或提供方扩展保存，不强迫体重、饮食等也有 cycle。

新来源的相同名字／单位不等于可直接合并。去重保留候选、依据和采用结果；无法可靠匹配时保留并明确未合并。

### 4.4 ContextRecord

目标、训练偏好、设备条件、用户确认的限制、作息和其他获准上下文，记录来源、生效区间、最后确认时间、状态。

用户事实与 AI 假设分开；模型不能静默把推测写入确认事实。撤回和更正传播到当前摘要。先结构化存储与普通检索，不引入向量数据库作为必需组件。

### 4.5 AnalysisRequest / AnalysisRun / EvidenceBundle

请求由受限的指标、范围、过滤、分组、配对和注册算法组成，服务端验证可用组合和计算预算。

运行记录包含：问题、请求参数、快照或输入版本、代码／计算定义版本、执行状态、结果引用、证据、限制、模型及提示词版本（使用模型时）。数据支持程度不伪装成统计或临床概率。

现有 EvidenceBundle 继续使用并版本化。它应支持按需取明细，而不是要求每个问题只读同一份日报。无论谁提出分析，数值都由代码产生并可复算。

### 4.6 PlanRevision / ProposedAction / ActionRun / Feedback

计划、建议、已确认版本、实际执行、采纳／拒绝和主观反馈分开记录。

动作包含目标对象和期望版本、结构化内容、幂等键、作用范围、有效期、确认凭据、风险类别和结果状态。服务端生成并校验确认凭据，不能信任模型自行提交的 `approved=true`。

审批绑定具体内容及版本。批准后内容变化、过期、目标变化均需重新处理；重复调用不能重复执行。已执行但网络响应丢失时允许查状态，不能盲目重试外发。

## 5. 查询与操作权限

| 操作类别 | 默认行为 | 后续空间 |
|---|---|---|
| 获准个人数据查询与确定性分析 | 已有范围授权内执行 | 可按需读取选定明细，不只日报摘要 |
| 新建日志／训练／计划草稿 | 显式用户请求或既有授权内执行 | 草稿不等于正式执行记录 |
| 修改本应用已存在记录 | 默认预览或确认；精确用户指令可作为明确授权，但由后端验证范围 | 用户可设置窄范围、可撤销的持续授权 |
| 对外发消息／导出到新接收方 | 校验接收方、内容范围和目的，必要时逐次确认 | 可以有已批准的固定日报通道，不强制永久禁用 |
| 删除数据、扩大权限、部署、增加费用 | 明确确认、影响范围和可恢复性检查 | 不因“早期少限制”跳过 |
| WHOOP 源数据写入／设备控制 | 本项目仍不提供 | 不虚构个人 API 没有的能力 |

工具注解、系统提示词、客户端审批都不是服务端权限的替代。鉴权、输入约束、幂等、审计和撤销状态由应用层执行。

持续授权记录发送目的、供应商、数据类别、范围、动作、期限和预算。同一范围不反复弹窗；变化时重新确认。同步、教练和分析工作区使用不同权限，不能共享全能凭据。

## 6. 稳定分析与探索分析

**稳定轨：** 已评测的指标、图表、日报和训练建议；有回归测试和明确适用限制。

**探索轨：** 自定义时间窗口、分组比较、行为假设、反例检查、个人实验记录。可以提出未证实的解释，但必须标为假设；新公式的运行结果标为实验派生值，不冒充 WHOOP 官方分数或临床结论。

最早版本使用注册函数和结构化请求即可。后续确需动态 Python 分析时，另建受控执行器：只挂载获准快照、无 WHOOP token、无默认网络、限时／内存／CPU、结果写独立区、检查输出。沙盒只降低执行风险，不自动证明分析方法正确；未经建立并测试，不提供任意代码工具。

探索产物经规则与回归验收后才升级到稳定轨。允许“尚无结论”也是有用产物，不强制每个问题产生训练调整。

## 7. 技术选型与可逆性

保留模块化单体。选择一个当前真正支持的数据库，SQLite 或已有合适的 PostgreSQL 均需结合实际环境；不要同时实现两套持久层只为宣称可扩展。第一批即提供迁移、备份一致性约定与恢复测试路径。

持久任务先用同一数据库的任务表和单工作进程，记录租约／执行状态／幂等键，按实际所需实现。不引入消息总线、完整事件溯源和插件市场。新计算函数的“注册”可以只是一个 Python 字典与接口测试。

模型默认、推理强度、允许供应商和成本可配置；可支持用户预先批准的回退策略，但每次降级必须显示，不静默改模型。不同模型的效果由评测比较，不能以名称新旧代替证据。

UI 可从轻量 Web 起步；共享服务是扩展接缝，不预先禁用将来有实际价值的丰富前端。未来连接器按实际 API／平台要求开发，空接口不标“已接入”。

## 8. 第一阶段实施重排

分组是能力依赖和验收单位，不是每跨一组都必须等待用户重说目标。

### F0 · 最小基础纵向验证

先审计当前仓库和权限，记录少量不可轻易逆转的决策，然后实现一个小闭环：合成 WHOOP 数据→受保护分层存储→一项趋势计算→EvidenceBundle→应用查询入口。并用一个普通手工／CSV 指标适配器检查来源解耦，用一个训练草稿／确认操作检查读写分界，用一次源修正检查重算。

MCP 尽早实现并做协议测试；实际客户端连接单独验证，环境受阻时不虚报成功。不要求完成全部图表、所有算法或完整动作平台才结束本批。无真实授权和付费模型时可完成合成闭环。

### F1 · WHOOP 数据覆盖与可靠接入

完成实际 OAuth、普通个人核心资源、分页、断点、回看、评分状态和单位语义；逐字段登记覆盖和真实验证。原始保留和真实数据落盘按来源政策与加密条件启用。持久任务不是本阶段结束以后才补。

### F2 · 日常使用与教练并行深化

完善看板、训练记录、个人上下文、日报周报、按需分析和实际 Codex／模型入口。界面与代理都复用服务，不强制先写完所有页面才做教练。实际采纳／拒绝反馈进入可追踪记录。

### F3 · 自动化与上线验收

按获准范围启用定时任务、可选 webhook、模型与通知；完成恢复演练、权限检查、独立验收与真实对账。安全从第一条真实数据开始，F3 是加强与最终验证，不是首次补安全。

## 9. 新增基础验收

以下是提议，初始均为 `not_run`。原包有用的 47 项测试不删除；受新权限设计影响的项目修改预期，而不是取消校验。

| 编号 | 验证 |
|---|---|
| X01 | 加入第二个手工／CSV 来源，不修改 WHOOP 同步代码 |
| X02 | 加入新注册指标，不修改原始接入表骨架、不强制重做所有工具 |
| X03 | Web 与 MCP 对同一服务请求返回相同输入版本与证据 |
| X04 | 源记录更正使关联派生结果失效，同一获准快照可以复算 |
| X05 | 查询历史“当时已知”状态不偷用后来获知的修正；缺历史明确不足 |
| X06 | 日志／计划写入有明确目标和范围，未经授权无法提交 |
| X07 | 审批绑定具体动作、期限和目标版本；篡改／过期／并发冲突拒绝 |
| X08 | 操作或任务重复调用不重复生效，崩溃恢复与撤销可解释 |
| X09 | 撤销外发授权立即阻止新外发，不自动删除仍获准的本地记录 |
| X10 | 来源保留／删除策略覆盖原始、规范化、派生、会话引用及恢复清单 |
| X11 | 模型不可用时核心服务工作；替换模型不迁移原始健康数据 |
| X12 | 探索分析明确标为实验；模型假设不会被静默存成用户确认事实 |
| X13 | 当前目标／限制过期或被修正后，不从旧对话复活 |
| X14 | 新模块源码和纯合成 fixtures 能入 Git，真实运行数据与秘密仍被排除 |
| X15 | 第一条真实数据落盘前已有授权、静态及传输保护核验；合成测试单独记录 |

## 10. 成功标准

首个版本功能可以有限，但增加一个合理的新来源、新问题、新指标或新操作，应主要新增适配器、计算函数或命令，而不是重写底座、复制一套统计、绕过权限或修改所有页面。
