# WHOOP Personal Copilot v1.0 独立架构审查

审查日期：2026-09-05。审查目标：减少不必要的早期限制，同时让核心基础能承载后续功能。

## 1. 范围与方法

直接解包并逐份阅读用户提供启动包的全部 26 个文件，共 1,229 行，包括项目规则、章程、架构、数据契约、分析、权限、47 项验收、阶段提示词、运行提示词和配置示例。原文件定位用 `路径:起始行–结束行`，行号来自原始 UTF-8 文件，不是改版后的行号。原包哈希和逐文件清单见 `evidence/REVIEW_MANIFEST.json`。

复核 WHOOP 官方 API、webhooks、API 使用条款，以及 OpenAI Codex MCP 配置、MCP 工具规范和 Git 忽略规则说明。压缩包无应用实现，不能据此判断实际程序的性能、可靠性或医学有效性。没有发现并声称“已证实的生产漏洞”；下文主要是设计和执行计划风险。唯一实际复现的配置问题是 R10。

## 2. 总体判断

**方向正确；数据工程防线值得保留；代理能力和开发顺序过度收窄；扩展契约尚不够明确。建议增量修订后实施，不建议推翻重做。**

原方案不是只有几张看板。它已经包含原始响应、规范化层、派生层、版本、删除、回看、数据质量、来源证据、可替换模型和模块化组件。这些不能为了显得审查“严格”而被错误描述为缺失。

需要改变的是：从“预先写好若干分析，模型只负责解释”的中心，转为“可信数据与应用服务是底座，分析和代理在受控能力上持续扩展”。这不要求微服务、大型插件平台、任意生产 SQL 或全电脑权限。

优先级定义：P1 为基础实施前应定清或修订，P2 为首个可用版本应解决。优先级表示返工／产品风险，不代表已经存在的漏洞严重度。

## 3. 应保留的设计

## 4. 发现与修订

### R01 · P1：模型角色被限制为固定统计的解释层

**定位：** `AGENTS.md:28`；`PROJECT_CHARTER.md:16`；`docs/ARCHITECTURE.md:39–41`；`docs/COACH_SPEC.md:6–20`。

**事实：** 原包已有多个查询工具，但核心规则要求模型只解释已验证结果，查询指标和聚合也预先限定。并非完全无法推理，而是没有给新分析需求一个明确的执行路径。

**风险：** 用户提出“排除旅行周、按训练时间分组、比较之后睡眠”的问题时，如果现有工具不支持，容易只能回答能力不足，或要求改代码增加专用工具。更强模型也被固定摘要的范围限制。

**修订：** 保留确定性数值计算，但让模型能够提出问题、生成受约束的分析计划、调用可组合分析工具、比较解释并保存待验证假设。生产查询使用结构化 `AnalysisRequest`，而非任意 SQL。已验证统计与探索结果分区显示。后续可增加隔离分析沙盒，不能直接给生产数据库和同步凭据。

**最小验证：** 同一分析工具完成两个未写成专用日报模板的问题；结果包含输入快照、参数、公式版本、证据和限制。不需要为了每个问题修改 WHOOP 同步器。

### R02 · P1：来源只读被扩展成整个代理永久只读

**定位：** `docs/COACH_SPEC.md:19–20,38–40`；`docs/SECURITY_PRIVACY.md:52–54`；`prompts/04_COACH_MCP.md:23`；`runtime_prompts/COACH_SYSTEM.md:41–45`。

**事实：** 原包允许用户通过 Web 修改本应用计划，但明确禁止模型工具写入、触发同步和发送通知。这是产品设计决定，不是 MCP 必须只读。[W02][W03]

**风险：** “帮我记录刚才的训练”“把周四计划挪到周五”必须跳到其他页面操作；后续主动助手和外部工作流都要推翻权限假设。

**修订：** WHOOP 官方源记录继续只读。外挂内部采用共享的查询服务和命令服务。读、创建草稿、执行已确认修改、外发、删除／管理分别授权。操作须有幂等键、目标版本、确认范围和审计；写入工具不持有 WHOOP refresh token。

**最小验证：** AI 能创建训练记录草稿；用户在当前会话或界面确认后可以提交一次；重复调用不重复写；确认后内容被篡改或目标版本变化会拒绝。源记录仍无法被修改。

### R03 · P1：已提到外部信息，但来源无关的领域契约仍偏薄

**定位：** `docs/ARCHITECTURE.md:36–43`；`docs/DATA_CONTRACTS.md:13–25`；`PROJECT_CHARTER.md:21–26`。

**事实：** 原包有 `metric_key`、来源、内部 ID、手工指标和导入，不是没有抽象。缺口在于未明确 Provider、SourceConnection、Observation、ProfileContext 等稳定契约；来源枚举仍以 WHOOP API／导出为中心。

**风险：** 新的体重来源、骑行文件或以后合法可用的数据源，可能被塞进 WHOOP 表和 WHOOP 日期逻辑，或者只保留成无法使用的 JSON。

**修订：** 保留具体的 sleep／workout／cycle 表，同时增加少量跨源公共字段和服务：内部 subject ID、来源连接、外部记录 ID、测量／事件时间与获取时间、定义／单位、版本和关联。WHOOP 的 cycle 是一种来源语义，不是所有健康数据必须属于的“天”。核心热字段强类型；未知字段保留扩展位；不要把全库做成一个万能 EAV／JSON 表。

**最小验证：** 使用 WHOOP 合成适配器和一个普通 CSV／手工身体指标适配器，证明第二来源无需改 WHOOP 代码；跨源冲突保留原值和采用理由，不按名字相同就双计或平均。

### R04 · P1：核心 Codex 价值验证过晚，阶段授权与依赖混在一起

**定位：** `AGENTS.md:13`；`ROADMAP.md:8–21`；`prompts/00_BOOTSTRAP.md:13–17,79–83`。

**事实：** M0 只写文档；M1 接全部资源；M2 统计；M3 完整看板；M4 才实现教练与 Codex。每个阶段都单独停止和等待授权。

**风险：** 可能完成许多数据和页面后，才发现工具契约不足、客户端不能连接或问答体验与目标不符。机械阶段停止也会迫使一个正常的跨层小闭环拆成多次沟通。

**修订：** 里程碑用于验收，不充当永久授权墙。在用户批准的工作批内按依赖实施；保留小提交、检查点和真实权限边界。先走通“少量数据→存储→统计→证据→实际查询入口”的纵向闭环，再扩全数据和完整页面。M0 可以包含必要、隔离的技术验证，不只产文档。

**最小验证：** 在完整看板之前，实际客户端或明确标注的协议测试客户端能取得带来源的数据；缺真实凭据只阻塞真实联调，不阻塞适配器和业务服务实现。

### R05 · P1：版本重算与持久任务已写在设计里，落实顺序却偏后

**定位：** `docs/ARCHITECTURE.md:70–76`；`docs/DATA_CONTRACTS.md:7–11,54–70`；`prompts/05_HARDEN_DEPLOY.md:11–15`。

**事实：** 原方案明确要求版本、失效和持久任务，但“实现持久化调度、故障恢复”等集中安排在 M5。不是缺少这些概念，而是存在先做脆弱同步、再重接任务基础的风险。

**修订：** 从第一条持久化数据开始就有迁移、幂等写、原始版本和任务状态。用同一数据库的轻量任务表即可，不必引入队列集群。保留测量时间、来源更新时间、应用首次／本次获知时间；回放只承诺重现应用当时已知的数据，不声称重建尚未采集的真实世界历史。未来回测不能悄悄使用后来修正的数据。

**理由：** WHOOP 有记录更新和删除通知，且 webhook 不是完整历史数据库；这些属于正常源行为，不是最后才处理的罕见边缘。[W04]

**最小验证：** 修改源记录后旧报告被标记失效；同一快照可重算；未完成任务重启后恢复而不重复生效；源删除不把本应用独立训练记录一并抹除。

### R06 · P1：API 使用条款没有进入原方案的基础核实清单

**定位：** `docs/SOURCES.md:6–23`；`docs/DATA_CONTRACTS.md:5–11`；`docs/SECURITY_PRIVACY.md:11–17`。

**事实：** 原包核实了技术接口，却未列入 API Terms of Use。当前条款涉及加密、外发许可、缓存／长期副本和竞争性用途。[W05]

**边界：** 这不等于本审查判断私人外挂被禁止；其中存在许可条件和适用解释问题，也不能凭“数据属于我”就断言所有官方计算结果可无限长期存储和再利用。本文不是法律意见。

**修订：** 增加轻量来源使用策略，记录来源、允许用途、同意、保留期／删除要求、条款核对日期与未决项。确认前不启用存在疑义的长期全量存档或扩散用途；合成原型和来源无关架构仍可继续。真实 WHOOP 数据第一次落盘前就核验保护措施，不把加密拖到最后发布。

**最小验证：** 保留期可按来源执行；撤销模型发送不影响仍被允许的本地查询；删除传播到快照、报告与备份恢复清单。长期原始保留受策略控制，不以“原始层”名义永久保存。

### R07 · P2：许可只有原则，没有能减少重复确认的持久授权模型

**定位：** `AGENTS.md:18,36–40`；`docs/SECURITY_PRIVACY.md:7–9,34–42`；`examples/config.example.json:29–44`。

**事实：** 原包要求外发同意，但没有规定每次都要确认；问题是授权粒度、持续时间和撤销语义不明确。不能将原文歪曲成必然每次弹窗。

**修订：** 用 `ConsentGrant` 记录目的、接收方、数据类别、范围、允许动作、期限、预算和撤销状态。在已批准范围内不重复提问；新增供应商、扩大字段、破坏性操作另行确认。开发 Codex、运行教练、分析工作区、同步服务采用不同能力；明确获准的分析工作区可以读选定明细快照，不必永远只有摘要。

**最小验证：** 同范围连续查询不中断；越界字段、过期授权和新接收方被拒绝；所有入口复用同一服务端权限检查。

### R08 · P2：长期个人上下文和建议反馈缺少明确的第一类记录

**定位：** `PROJECT_CHARTER.md:41`；`docs/DATA_CONTRACTS.md:84`；`docs/COACH_SPEC.md:13–16,38–40`。

**事实：** 原包有个人档案、主观记录和计划，但没有明确“确认事实、偏好、当前限制、模型假设、建议采纳和实际结果”的存储与失效约定。

**风险：** 每次读数都很新，教练却不理解目标变化和之前建议是否有用；或者把一次模型推测错误地当成永久个人事实。

**修订：** 先用简单结构化表／记录保存上下文和反馈，不需要向量数据库。记录信息来源、生效时间、确认时间、失效时间；模型提出的假设与用户确认的事实分开。建议→采纳／拒绝→实际执行→主观反馈构成可追踪链，不自动把反馈当作因果证据。

**最小验证：** 过期目标不会继续当当前目标；撤回错误记忆后不会由旧会话摘要重新进入；能看到同一建议被采纳与否。

### R09 · P2：验收较完整，但尚未证明“增加玩法不用重建核心”

**定位：** `docs/ACCEPTANCE_TESTS.md:14–80`；`docs/ARCHITECTURE.md:25–45`。

**事实：** 原包 47 项主要覆盖功能正确性、边界与安全，缺少第二来源、新指标、新工具／入口和算法升级的变化测试。

**修订：** 不急着建动态插件系统，只增加少量扩展演练：新来源不改 WHOOP 同步；新指标不改存储骨架；同一服务从 Web 和 MCP 得到相同证据；换模型不迁移原始数据；计算版本升级可以从允许保留的快照重算。

**最小验证：** 使用测试内第二适配器和新计算函数完成这些演练。迁移工具的存在不等于未来数据库更换已经得到验证；首期只正式支持一种数据库。

### R10 · P2：`.gitignore` 会误忽略未来导入模块和合成测试数据

**定位：** `.gitignore:7–8` 与 `docs/ARCHITECTURE.md:40`。

**复现：** 在独立临时 Git 仓库中复制原忽略文件并创建纯合成占位文件，执行 `git check-ignore -v`：

```text
.gitignore:8:imports/  src/whoop_copilot/imports/parser.py
.gitignore:7:data/     src/whoop_copilot/data/models.py
.gitignore:8:imports/  tests/fixtures/imports/sample.csv
```

无前导根路径的目录模式可匹配下级同名目录，这与 Git 官方规则一致。[W06] 该结果证明命名碰撞风险，不证明当前有代码已经丢失；原包没有应用代码。

**最小修订：** 将运行数据集中到项目外或明确的 `/private/`／`/runtime/` 路径。兼容旧根目录时使用 `/imports/`、`/data/` 等根限定规则，保留 `.env`、密钥、数据库和日志文件的防误提交规则。示例与实际回归输出在本包中。不要用全面取消忽略来解决源码遗漏。

### R11 · P2：同一产品限制在多处重复，单独增加“开放版提示词”不够

**定位：** `AGENTS.md:13,28–30,38`；`ROADMAP.md:4–21`；`docs/COACH_SPEC.md:20,40`；`runtime_prompts/COACH_SYSTEM.md:43–45`；`prompts/00_BOOTSTRAP.md:59,67,79–83`。

**风险：** 若只追加一份新架构建议，旧根规则仍禁止写入／跨阶段，代码任务和运行教练将继续互相矛盾。

**修订：** 对原有权威文件进行一致性修订；保留来源和测试历史。根 AGENTS 保持短小，领域细节引用对应规范；阶段提示词引用权威规范，不全文复制多套政策。新增文档只服务实际契约或测试，不为了“打基础”继续膨胀文件数量。

## 5. 建议的决策

采用 `FOUNDATION_REVISION_SPEC.md` 的“模块化单体＋来源无关数据契约＋受控代理操作＋稳定／探索双轨分析”。不把全部未来功能实现放进第一阶段，但把接入、查询、计算、动作、上下文和结果来源的接缝做好。

首个闭环应包含最少量的合成数据贯通、第二来源接入演练、带证据查询、一个草稿／确认写入操作和源修正重算；真实 WHOOP 授权、模型调用和网络部署分别在获准后验证。完整看板不再是体验 Codex 的前置条件。
